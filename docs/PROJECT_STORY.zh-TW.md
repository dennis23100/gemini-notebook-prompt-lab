# 專案故事

## 從真實教學問題變成開源工具

Gemini Notebook 提示詞工作室並不是從「Prompt 越多越好」開始，而是從一個教學問題開始：**同一份可信來源，面對不同受眾時，文字、節奏、資訊密度與視覺呈現往往需要調整。**

這個專案受到真實教學經驗影響，其中包含一次**台下 100+ 位聽眾**的實體教學分享。這段經驗讓我們更確定：除了內容正確之外，受眾適配同樣重要。

專案把這個想法整理成可重複使用的流程：

```text
可信來源
  ↓
受眾適配
  ↓
視覺／產出方向
  ↓
來源限定 Prompt
  ↓
Gemini Notebook
  ↓
檢查／驗證
```

## 「100+ 位聽眾」代表什麼？

它是專案起源的真實背景，證明這個問題來自實際教學，而不是為了做 GitHub 專案才臨時想出來的情境。

但它**不代表**：

- 100+ 位 GitHub 使用者；
- 100+ 次安裝；
- 每一位現場聽眾都使用過目前這個 repository；
- 現在這個 Web App 當時已經上線。

我們會把這些數字分開，不混淆使用量與教學經驗。

## 公開影片／照片原則

目前有一段實體教學短片。要放進公開 repository 前，應先檢查：

- 是否有可辨識的現場參與者；
- 活動對公開影像的授權／期待；
- 投影畫面是否包含不應公開的資訊；
- 用一張經過處理的截圖是否比整段影片更安全、更清楚。

之後可以把經過隱私檢查的截圖或短片放進 README 與發佈素材，目的只是說明「這個問題從哪裡來」，不會拿來膨脹 GitHub 使用量。

## 接下來真正要證明的事情

下一步最重要的是讓開源專案自己產生證據：

```text
真實使用者
→ 回饋 / Issue
→ 分流與判斷
→ 修正或 PR
→ 測試
→ Release
→ 回訪
```

這條維護鏈，比單純累積被動 Star 更有價值。
